## 1. 重開機後常駐在跑但完全不畫

**現象**：2026-09-30 重開機後桌布不動。`launchctl` 顯示 running、沒有退出紀錄；log 從啟動第一秒起就一直是
`visible screens=2/2 fps=0.0 [0/0] steps=0`，連模擬都沒推進（`steps=0`＝`draw(in:)` 根本沒被呼叫）。
沒有 SUSPENDED、沒有 OCCLUDED，MTKView 也沒 pause。

**根因**：LaunchAgent `RunAtLoad` 在登入極早期就啟動 wall42，MTKView 內部的 display link 建在
尚未就緒的螢幕上，之後永遠不觸發。旁證：重開機後主螢幕 displayID 由 `1` 變成 `3`。
`launchctl kickstart -k` 手動重啟後立即 30fps，確認與程式狀態無關、是啟動時機問題。

**修法**：`report()` 內加看門狗。條件＝沒有手動暫停、至少一個畫面沒 pause、不在剛切換的 1.1 秒內、
該秒 0 幀；連續 5 秒就呼叫 `rebuildSurfaces`（等同螢幕配置改變時的重建）。最多連試 3 次，
一旦有畫出來就歸零，避免真的壞掉時無限重建。

**驗證**：`WALL42_SIMULATE_STALL=1 WALL42_DURATION=14 ./wall42` —— 第一批畫面不接 renderer，
log 顯示 0 幀 4 秒 → `⚠ 該畫卻連續 5 秒 0 幀…重建畫面（第 1 次）` → 下一秒回到 29–30fps。
真實開機情境要等下次重開機，看 log 是否出現該行並恢復。

## 2. log 每秒一行、無上限

**現象**：`~/Library/Logs/wall42.log` 每秒一行統計，4 天 26.7 萬行、28MB，會一直長大。

**限制**：`bench.sh`／`bench_cpu.sh` 靠每秒那行解析 fps／cpu，不能直接拿掉。兩者都會設 `WALL42_DURATION`。

**修法**：
- `WALL42_DURATION>0` 或 `WALL42_VERBOSE=1` → 維持每秒一行；常駐 → 60 秒一行。
- 事件（焦點、遮擋、重建…）照常當下寫；異常（SUSPENDED/OCCLUDED 仍在繪製、0 幀）不受節流。
- stdout 是一般檔案且超過 20MB → `ftruncate` 清空（啟動時與每 10 分鐘檢查；launchd 用 append 開檔，外部輪替做不到）。

**驗證**：預先塞 22MB 假 log，以 `>>` 接 wall42 輸出 → 啟動即清空，啟動訊息完整保留，10 秒內只有 1 行統計。

## 3～5：09-30 常駐 17 小時 log 覆盤（04:13–21:13，1,021 筆分鐘統計）

**整體健康**：fps 平均 30.0（27.1–31.1），沒有掉幀；記憶體第一小時 108→127MB 後持平，無洩漏；
log 17 小時 112KB（#2 修正生效）；看門狗尚未觸發（期間沒重開機）。

**#3 沒人在看也整夜全速畫**
- 17 小時內 **0 次 SUSPENDED、0 次 OCCLUDED**：一次都沒停過。
- `pmset`：`displaysleep 0 (display sleep prevented by Google Chrome)`，螢幕永遠不會休眠，所以休眠停畫從來沒機會觸發。
- 焦點事件在 05:41→11:59（6.3 小時）、12:30→17:57（5.5 小時）完全空白，推定無人操作，但照畫 30fps、CPU 4.8–6.9%。
- 方向：用 `CGEventSource.secondsSinceLastEventType`（HID 閒置秒數）判斷，閒置超過 N 分鐘就降到低 fps 或暫停，一碰滑鼠鍵盤立即恢復。N 與閒置時的行為（暫停／降速）待拍板。

**#4 兩台都全速**
- 分鐘統計中 49% 是兩台同時 30fps；12:00–20:00 幾乎 100%。
- 兩台全速 CPU 平均 6.72%，一台降速 5.12%，差 1.6 個百分點（約 +31%）。
- 原因：`updateFocus` 把「滑鼠所在螢幕」和「前景 App 視窗所在螢幕」都算焦點；滑鼠停在另一台不動，那台就一直全速。
- 方向：滑鼠只有最近 N 秒內有移動才算焦點；停著不動就只看前景視窗。

**#5 log 缺閒置欄位**
- 分鐘統計加 `idle=秒`，之後覆盤能直接分辨「有人／沒人」時段，不必從焦點事件推。

### 3～5 處理結果（2026-10-01）

- **#3**：`motion.idle`（全部 Optional）。閒置 ≥600 秒 → 5fps，≥1800 秒 → 1fps（不暫停，最後畫面保留、不會變黑）。
  閒置秒數取自 `CGEventSource.secondsSinceLastEventType`，不需要輔助使用權限；每秒檢查，一有輸入 1 秒內恢復。
  驗證（`WALL42_SIMULATE_IDLE=1` 把閒置改成啟動後秒數，門檻縮成 4／9 秒）：
  30fps cpu 1.6% → 5fps 0.6% → 1fps 0.44%；真實輸入測試：閒置 3 秒降速、動滑鼠後下一秒回 30fps。
- **#4**：滑鼠最近 10 秒有移動才算焦點；停著不動只看前景視窗所在螢幕。
- **#5**：分鐘統計尾端加 `idle=秒`（bench 的正規式只抓前面欄位，不受影響）。

## 6. 常駐版 CPU 比終端機跑的同設定高 2 倍以上（待查）

- 同一份 config、同為 2 螢幕 30/15fps：終端機直接跑 `./wall42` 約 1.6%；LaunchAgent 常駐版 `ps` 量 20 秒 3.9%，
  09-30 分鐘統計 5–7%。
- 懷疑與排程 QoS 有關（plist 已設 `ProcessType=Interactive`，之前 Background→Interactive 已從 5 倍降下來，
  但從終端機啟動會繼承前景 App 的責任歸屬／QoS）。下一步：`taskinfo`／`powermetrics` 比較兩者的 P/E-core 分布與 QoS。
